Pane manager

A local server owns real PTY-backed processes. The CLI is a thin client over a Unix socket. This is what the Claude skill drives.

  • spawn · list · send · read · kill
  • Detached server, auto-started on first use
  • Not yet shown in the TUI mockup above

architecture

One binary, two paths that don't meet yet

Both halves ship in the same sieg executable and branch on argv. The left path is pure rendering of fake data. The right path is a real client/server split: the CLI never touches a PTY directly — it asks a detached background server to, over a local socket.

pane manager

CLI reference

The first spawn auto-starts the server if it isn't already running. Panes keep running after the shell that spawned them exits.

commandwhat it does
sieg spawn <name> -- <cmd...>Starts a real background pane running <cmd...>. Fails if <name> is already registered, running or exited.
sieg listLists every pane with its status (running or exited(<code>)) and the command it was started with.
sieg send <name> <text...>Writes <text...> plus a newline to the pane's stdin, as if typed.
sieg read <name> [lines]Prints the pane's buffered output (stdout+stderr, PTY-merged, capped ~200KB). Optionally just the last N lines.
sieg kill <name>Terminates the process. Status becomes exited; the name stays reserved — there's no remove yet.
# run from source $ cargo run # the visual TUI mockup $ cargo run -- list # the real pane manager CLI

claude code integration

The Sieg skill

The repo ships skills/sieg/SKILL.md, which teaches Claude Code to drive the pane manager above — this is the piece that makes the CLI more than a manual tool.

$ npx skills add daymer-perdomo/sieg --skill sieg -g

When Claude reaches for it

  • Running something long (a dev server, a build watch, a test suite) without blocking the conversation — spawn it, read it back later.
  • Running several things concurrently and checking each independently, one distinct name per task.
  • Answering an interactive prompt inside a background process via send.
  • Killing a pane that's stuck or was started by mistake.

Timeline

Visual mockup, separate from herdr-v2

Built in its own folder, hand-copying herdr's real catppuccin palette and roughly matching its sidebar/tabs/panes/onboarding layout — with fully hardcoded data. No dependency on herdr's code.

02

Renamed herdr → Sieg

Package, binary, UI text and repo renamed throughout; first to sieg-ui-mockup, then trimmed to just sieg.

03

Real distribution set up

Public GitHub repo, a release workflow building macOS binaries on tag push, and a curl | sh install script — mirroring herdr's own install flow.

04

Moved to the correct GitHub account

First created under daymer003 by mistake; re-created under daymer-perdomo once authenticated, with every reference repointed.

05

Fixed the release workflow

The x86_64 build used a macos-13 runner that was badly queue-congested (10+ minute waits). Switched to cross-compiling both targets on one macos-14 runner.

06

First real functionality: the pane manager

Added the socket server, the spawn/list/send/read/kill CLI, and skills/sieg/SKILL.md — shipped as v0.2.0.

not done yet

Roadmap

  • Wire the TUI mockup to the real pane manager — show actual sieg list state instead of data.rs's hardcoded panes.
  • Agent state detection (idle / working / blocked) — today sieg list only reports process running/exited, nothing like herdr's detection engine.
  • A sieg remove command, so an exited pane's name can be reused without restarting the server.
  • An in-binary update check (sieg update) — installs are currently a fully manual re-run of the curl script.
