Pane manager + CLI

A local server owns real PTY-backed processes. The CLI and the TUI are both thin clients over the same Unix socket — spawn from one, see it in the other.

  • spawn · list · send · read · kill
  • Detached server, auto-started on first use
  • What the Claude skill drives

architecture

One binary, two entry points, one server

The TUI and the CLI both branch off the same sieg executable, and both go through the same client.rs to reach the same server — spawn a pane from one, and it shows up in the other immediately, because there's only one source of truth. The only difference is cadence: the CLI makes one request per command; the TUI polls continuously to stay live.

pane manager

CLI reference

The first spawn auto-starts the server if it isn't already running. Panes keep running after the shell that spawned them exits.

commandwhat it does
sieg spawn <name> -- <cmd...>Starts a real background pane running <cmd...>. Fails if <name> is already registered, running or exited.
sieg listLists every pane with its status (running or exited(<code>)) and the command it was started with.
sieg send <name> <text...>Writes <text...> plus a newline to the pane's stdin, as if typed.
sieg read <name> [lines]Prints the pane's buffered output (stdout+stderr, PTY-merged, capped ~200KB). Optionally just the last N lines.
sieg kill <name>Terminates the process. Status becomes exited; the name stays reserved — there's no remove yet.
# run from source $ cargo run # the TUI $ cargo run -- list # the pane manager CLI

claude code integration

The Sieg skill

The repo ships skills/sieg/SKILL.md, which teaches Claude Code to drive the pane manager above — this is the piece that makes the CLI more than a manual tool.

$ npx skills add daymer-perdomo/sieg --skill sieg -g

When Claude reaches for it

  • Running something long (a dev server, a build watch, a test suite) without blocking the conversation — spawn it, read it back later.
  • Running several things concurrently and checking each independently, one distinct name per task.
  • Answering an interactive prompt inside a background process via send.
  • Killing a pane that's stuck or was started by mistake.

Roadmap

  • A real terminal emulator (cursor grid, color) instead of the linear scrollback interpreter — needed for full-screen programs (vim, htop) to render correctly.
  • Agent state detection (idle / working / blocked) — today sieg list only reports process running/exited, nothing like herdr's detection engine.
  • A sieg remove command, so an exited pane's name can be reused without restarting the server.
  • Multiple panes on screen at once (split view) — the TUI currently shows one focused pane at a time.
  • An in-binary update check (sieg update) — installs are currently a fully manual re-run of the curl script.
